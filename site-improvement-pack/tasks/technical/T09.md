## Goal

Optimise only after measuring a current baseline; create page-specific social assets without adding runtime weight.

## Why this task exists

- The static architecture, system fonts, small JavaScript and explicit image dimensions are already strong.
- No Lighthouse or field CWV score was measured in the original audit.

## Implementation requirements

- Measure Lighthouse mobile/desktop locally and record date, environment and limitations.
- Identify the actual LCP element on key pages.
- Inspect image dimensions, formats, srcset, lazy loading and preload use.
- Create page-specific 1200×630 OG images for materially different intents using system-safe assets and readable text.
- Keep only the current page's likely LCP asset high priority.
- Optimise oversized images and add AVIF only when fallback and measurable benefit are clear.
- Profile the pointer-following effect before changing it; throttle via `requestAnimationFrame` only if needed.
- Set internal budgets after baseline, not arbitrary marketing claims.
- Update image sitemap for real public images.
- Do not add custom web fonts or heavy animation.

## Non-goals

- No invented PageSpeed score.
- No optimisation that degrades portrait quality or accessibility.
- No runtime analytics.

## Acceptance criteria

- A reproducible baseline report exists.
- No asset is obviously oversized for its rendered dimensions.
- Key pages have distinct, correct OG assets.
- LCP preload/priority is intentional.
- CLS safeguards remain through explicit dimensions/aspect ratios.
- Static and browser QA pass.

## Verification

- Run Lighthouse in a documented environment.
- Check network requests and total transfer size.
- Validate OG image URLs and dimensions.
- Compare screenshots before/after.

Always run:

```bash
node qa/check.mjs
```

Run any additional task-specific test introduced by the implementation.
